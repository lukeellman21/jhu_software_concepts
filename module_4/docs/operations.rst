Operational notes
=================

Busy-state policy
-----------------

One flag, :attr:`src.flask_app.PullState.busy`, gates both POST endpoints:

.. list-table::
   :header-rows: 1
   :widths: 30 20 50

   * - Request
     - Busy?
     - Response
   * - ``POST /pull-data``
     - no
     - ``200 {"ok": true, "rows_loaded": n}``, or ``202`` with a background
       runner
   * - ``POST /pull-data``
     - yes
     - ``409 {"ok": false, "busy": true}``; nothing is scraped or written
   * - ``POST /update-analysis``
     - no
     - ``200 {"ok": true, "updated_at": ...}``
   * - ``POST /update-analysis``
     - yes
     - ``409 {"ok": false, "busy": true}``; the snapshot is left alone
   * - ``POST /pull-data`` (loader raised)
     - --
     - ``500 {"ok": false, "error": ...}``; the batch was rolled back

The flag is set before the job starts and cleared in both the success and the
failure path, so a failed pull cannot wedge the pipeline.  ``GET /status``
exposes the same state as JSON, which is how the page and the tests observe it
without polling the database.

Analysis caching
----------------

``GET /analysis`` renders the cached snapshot on
:class:`src.flask_app.PullState`, computing one on first visit.  A pull does
**not** refresh it -- that is what the **Update Analysis** button is for.  The
page shows the timestamp of the last update so a stale snapshot is visible
rather than silent.

Idempotency and uniqueness
--------------------------

``p_id`` is the primary key and is derived from the record rather than
generated by the database (:func:`src.load_data.derive_p_id`):

1. an explicit ``p_id`` or ``id`` on the record, if it is an integer;
2. otherwise the numeric id in the Grad Café result URL
   (``.../result/1020482`` → ``1020482``);
3. otherwise a SHA-256 fingerprint of ``program``, ``comments``,
   ``date_added`` and ``status``, reduced to a 31-bit integer.

Inserts use ``ON CONFLICT (p_id) DO NOTHING``, so:

* pulling the same page twice inserts nothing the second time;
* overlapping pulls insert only the records the database has not seen;
* :func:`src.load_data.insert_rows` returns the number of genuinely new rows,
  which is what the endpoint reports as ``rows_loaded``.

Failure handling
----------------

The whole batch is one transaction.  Any ``psycopg.Error`` rolls it back and
re-raises, so a bad row in the middle of a pull cannot leave a partial write
behind.  The endpoint turns that into a ``500`` and records the message on the
state, where the page renders it as an error banner.

Required fields
---------------

:data:`src.load_data.REQUIRED_FIELDS` lists the columns that may never be
``NULL``.  :func:`src.load_data.normalize_record` fills each of them with a
documented fallback (``"Unknown"``, ``"Applied"``, ``"Other"``, ``""``), and
the table declares them ``NOT NULL`` so the guarantee is enforced where it
matters.

Background pulls
----------------

The default runner is synchronous: the response arrives after the load
finishes.  Passing ``runner=run_in_thread`` to
:func:`src.flask_app.create_app` moves the job to a daemon thread; the endpoint
then answers ``202`` and the caller watches ``GET /status`` for completion.
